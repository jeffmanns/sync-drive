# What an Update records: a log on the Mac, and a last-updated marker on the Replica

#11 asks for a log of each Update on the Mac and a marker on the Replica saying when it was last updated, which Start shows before comparing. ADR 0017 left one question for this ticket: an Update limited to one folder does not bring the whole Replica up to date, so the marker must not suggest it does. These are the answers, made while building #11. The owner reviews them in the PR.

## The decision

- **The last-updated marker is a hidden file, `.sync-drive-last-updated`, at the top level of the Replica.** It is plain JSON. Like the Holding area and the Incoming folder, comparisons skip it on the Replica, and a Primary holding an item with its name, in any letter case, stops the comparison (ADR 0007). Otherwise an Update would copy the Primary's item over the marker.
- **An Update limited to one folder is recorded apart from the whole drive.** The marker holds the date of the last Update of the whole drive, and, for each folder updated on its own since, the date of the last Update of that folder. An Update of the whole drive clears that list. Start says "Replica last updated 3 months ago, on 20 August 2026", then lists each folder updated since, as "only the folder" updated. When the whole drive has never been updated, Start says so. A folder-limited Update never moves the whole drive's date.
- **Only an Update that finishes is recorded.** The marker is the last thing `update()` writes. An Update that stops partway, or is refused before writing, leaves the marker as it was. A comparison that finds nothing to update is not an Update, and records nothing.
- **An Update that finished but left undone something the owner wanted done is recorded as partial,** with how many items it left undone: files not copied, renamed or moved into the Holding area, content mismatches with no choice made, and items on the Primary that could not be read. Start then says "Replica last partly updated today, on 24 November 2026. 3 items were left undone.", and the same for a folder, and points to the Update logs, which list each item and why. What the owner chose to leave does not make an Update partial: declined Moves or deletions, and content mismatches kept as chosen. The Replica is then as the owner chose. To tell a mismatch kept as chosen from one with no choice made, `update()` is given the kept ones as `Approvals.keep`.
- **An Update limited to a folder that is gone from the Primary is not recorded.** It brought nothing in that folder up to date (ADR 0017 leaves every deletion in place), so a date would say otherwise.
- **The marker is written under a temporary name in the Incoming folder and renamed into place,** so a half-written marker is never left behind. If it cannot be written, the Update has still finished, having done everything else: it is not reported as stopped. `UpdateResult.notRecorded` says why the marker does not record it, for this and for a gone folder, and the Result and the log say: "This Update finished, but its date was not saved on the Replica, because …. Start will go on showing the date of the Update before it." An earlier date understates the Replica, which is the safe way to be wrong.
- **The marker carries a format version,** `"version": 1`, so a later sync-drive can change the format without calling older markers damaged. New fields may only be added, since readers ignore fields they do not know. A change that renames, removes or reshapes a field raises the version, and that version of sync-drive must still read every earlier version. A marker from a newer version of sync-drive is reported as such, not as damaged: Start says "The record of when the Replica was last updated was written by a newer version of sync-drive. Update sync-drive to see it; an Update with this version replaces it." Comparing works as usual, and the next Update with the older app replaces the marker, as it does a damaged one. A marker with no version, or one that is not a positive whole number, is damaged.
- **A damaged marker does not stop anything.** Start says it is damaged, comparing works as usual, and the next Update replaces it. A folder-limited Update that replaces it records only its folder, so the whole drive's date is then unknown rather than wrong.
- **Each Update is logged on the Mac in a new plain-text file** in an `Update logs` folder beside the Pairing (`~/Library/Application Support/sync-drive/Update logs/`), named by when it ended: `2026-11-24 10.30.05 Update.txt`. A log never replaces an earlier one. It records the drives, the Folder limit, Quick compare or Deep verify, and then what the Result shows: the files copied, the content mismatches overwritten, and those left as they are with the reason (kept as chosen, or no choice made), the Moves renamed (old path → new path), the files moved into the Holding area, what was deleted for good from the Holding area, every file not copied, renamed or moved with its reason, and what was unreadable on the Primary. An Update that stopped partway is logged too, with why it stopped. If the log cannot be written, the Result says so; the Update itself is not affected.
- **The Result reads the Holding area again after the Update** and shows what it holds, which may include files from an earlier Update (ADR 0006), and the day it was last added to, as its `READ ME.txt` gives it. Then it reminds the owner how to restore a file. `update()` reports whether it emptied the Holding area, so the log says what was deleted for good only when it was.

## Considered Options

- **A folder-limited Update leaves the marker alone:** simpler, but Start would then say nothing about Updates the owner did make. An owner working through the drive folder by folder would see only an old date.
- **A folder-limited Update moves the marker's date:** Start would then call a Replica up to date when most of it was not.
- **Recording every Update, even one that stopped:** the marker would then say "updated today" after an Update that was cut short.
- **Recording a partial Update as if it were complete:** Start would say "updated today" when files the owner wanted copied were not.
- **Recording only complete Updates:** Start would show a date months old after an Update that copied all but a few files, understating the Replica as much as the above overstates it.
- **Counting declined deletions and Moves as left undone:** an owner who keeps the Replica's extra files on purpose would never see it as up to date.
- **Reporting a marker that cannot be written as the Update stopping:** untrue, as everything else was done, and it would hide what was.
- **A marker with no format version, relying on the damaged-marker path when the format changes:** simpler, but a planned change of format would make Start show an untrue "damaged" message, and a folder-limited Update would then lose the whole drive's date and every other folder's until the next Update of the whole drive.
- **The marker in the Holding area's `READ ME.txt`:** the Holding area is emptied and rewritten only by Updates with deletions, so it would often be out of date.
- **Logs in `~/Library/Logs`:** Console would show them, but keeping them beside the Pairing puts everything sync-drive keeps on the Mac in one folder, and the tests can point it elsewhere with the Pairing.

## Consequences

- `UpdateResult` has `emptiedHoldingArea` and `notRecorded`, and `Approvals` has `keep`.
- Each date in the marker is `{ "updated": …, "leftUndone": 3 }`, with `leftUndone` only when the Update was partial.
- The marker begins with `"version": 1`. Adding a field leaves the version as it is; any other change to the format raises it, and must come with a way to read the earlier versions.
- `readHoldingArea()` also gives the day in the `READ ME.txt`, from the wording before and after ADR 0018.
- A Replica updated before #11 shows as never updated as a whole until its next Update of the whole drive.
